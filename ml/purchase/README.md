# Reproducing the purchase extraction experiments

**Latest work:** use the [v2 reproduction notes](V2.md) and [v2 results](../../docs/purchase-ml-v2-report.md) for the line-decision adapter and memory-bounded training. The commands and results below preserve the v1 baseline.

Read [the actual results and deployment report](../../docs/purchase-ml-cloud-report.md) first. This is synthetic purchase-text evaluation, not the earlier clothing-photo benchmark.

`data/evaluation/purchase-v1` contains 300 train / 60 validation / 60 test documents generated by `prepare.py`. Families and source hashes are disjoint; vocabulary overlaps. `base-manifest.json` pins the Apache-2.0 Qwen2.5-0.5B-Instruct revision and file hashes. `prompt.json` exports the application prompt/schema, and the Node bridge calls the real application validator.

The actual 120-step training attempt stopped at step 71 with CUDA OOM. The evaluated artifact is checkpoint 40. Its local path is `ml/checkpoints/purchase-lora-v1/adapter/adapter_model.safetensors`, 35,237,104 bytes, SHA-256 `6817041bfab2a1ea0b16840813b6414078b57d96a91eb023e1690b773d23933a`. It is not uploaded to GitHub. Recovery checked finite safetensors and did not load optimizer pickle state. Do not substitute the base model and call it tuned.

Use Python 3.12 and pinned `requirements.txt` inside a virtual environment. The actual run used PyTorch 2.6.0+cu124 from the official PyTorch index. Full dependency versions and the failure log are under `output/purchase-ml/training/`.

```powershell
python ml/purchase/prepare.py
python ml/purchase/download_model.py
python -m unittest discover -s ml/purchase -p test_evaluation.py
python ml/purchase/evaluate.py --mode rules --split test --out output/purchase-ml/rules-test
python ml/purchase/train.py --steps 120 --output ml/checkpoints/new-purchase-run
python ml/purchase/evaluate.py --mode base --split test --out output/purchase-ml/base-test
python ml/purchase/evaluate.py --mode adapter --split test --out output/purchase-ml/adapter-test
node scripts/purchase-evaluation-bridge.mjs ollama data/evaluation/purchase-v1/test.jsonl output/purchase-ml/ollama-test-raw.json
python ml/purchase/evaluate.py --mode records --records output/purchase-ml/ollama-test-raw.json --split test --out output/purchase-ml/ollama-test
```

Training requires a fresh directory and can fail on this 8 GB GPU. Review memory before rerunning. Early diagnostic files are now saved before optimization; those files were not emitted by the original failed run. Test-driven model changes require a new untouched test set. Base/adapter use identical unconstrained generation, while Ollama uses the application's existing schema-constrained protocol. Read `output/purchase-ml/execution-context.json` before interpreting latency.

The experimental server and worker run with `python ml/purchase/serve.py` and `node scripts/purchase-worker.mjs --candidate`. Both model services stay on loopback. The normal command `npm run imports:worker` uses the existing Ollama model. The adapter remains opt-in because it missed garments. Keep the worker configuration in ignored `.local-data/deployment/purchase-worker.json`; never use a service-role key or expose model ports.

Migrations 003–005 and a seven-day credential are already applied to the current project. **Do not rerun initial provisioning:** the helper packages table creation, not idempotent upgrade orchestration. Apply only new numbered migrations to an existing installation. Credential renewal remains an explicit operational action.

The SQL experiment rolls back experimental wardrobe writes. The HTTPS fixture experiment measures transport only; `scripts/experiment-purchase-candidate.mjs` uses the real saved adapter. Do not run these seed/claim scripts against a busy production queue or count synthetic drafts as owned garments.
