# Purchase extraction v2: reproduction and serving

This is the purchase-text adapter, not a photo-recognition model. The v1 implementation and its failed GPU run remain intact. Read the [v2 evaluation report](../../docs/purchase-ml-v2-report.md) for the measured outcome and remaining failures.

## Training protocol

Use the existing Python 3.12 environment and pinned dependencies in `requirements.txt`, including PyTorch 2.6.0+cu124. The base model is the revision and hashes in `base-manifest.json`. No remote model code, cloud training, private receipts or paid inference is used.

The committed v2 dataset is frozen at 600 train / 100 validation / 100 new test receipts. Do not regenerate it over the existing files. `v2_prepare.py` documents its construction; it refuses to overwrite the dataset. Test cases share clothing vocabulary with training, while merchant/template families and complete source hashes are separate. The old 60-document test is now a regression set, not an unseen holdout.

The model receives one line and generates seven compact fields. Deterministic code checks copied values and creates the original application evidence schema. There is no hidden vocabulary parser substituting for the model in these candidate scores. Missing, malformed or ungrounded line decisions reject the receipt; they do not become a successful empty response.

Training uses LoRA rank 16 / alpha 32 / dropout 0.05, all seven attention/MLP projection types, BF16, batch one, accumulation eight, 300 optimizer steps and cosine learning rate 0.0002 with a 15-step warmup and 10% floor. Sampling is balanced between clothing and non-clothing lines. Python sampling uses seed 29; the parity preflight sets the torch RNG to 17 before adapter initialization. Each training sequence is bounded at 768 tokens without silent truncation; actual generated training sequences are shorter.

`v2_loss.py` computes shifted causal cross entropy only at supervised positions and checkpoints 32-token vocabulary chunks. Decoder checkpointing uses `use_reentrant=False`. Dense/chunked scalar losses and gradients are compared on a float32 toy problem. The real-model BF16 preflight records both loss and memory for the same batch; small BF16 differences are retained rather than described as bit-identical.

Checkpoints at steps 100, 200 and 300 are selected by generated validation clothing recall, then precision, field accuracy and exact-document count. Training loss does not select the winner. The final test is evaluated after selection. Training output must go into a fresh `ml/checkpoints/purchase-lora-v2` directory; preserve an earlier run before starting another.

```powershell
.\ml\.venv\Scripts\python.exe -m unittest discover -s ml/purchase -p 'test_*.py'
.\ml\.venv\Scripts\python.exe -u ml/purchase/v2_train.py
.\ml\.venv\Scripts\python.exe ml/purchase/v2_artifact.py
.\ml\.venv\Scripts\python.exe -u ml/purchase/v2_run_evaluations.py
.\ml\.venv\Scripts\python.exe ml/purchase/v2_format_diagnostic.py
node scripts/purchase-evaluation-bridge.mjs rules data/evaluation/purchase-v2/test.jsonl output/purchase-ml-v2/runtime-parser-raw.json
$env:PURCHASE_EVAL_DATASET='purchase-v2'
.\ml\.venv\Scripts\python.exe ml/purchase/evaluate.py --mode records --records output/purchase-ml-v2/runtime-parser-raw.json --split test --out output/purchase-ml-v2/runtime-parser-test
Remove-Item Env:PURCHASE_EVAL_DATASET
.\ml\.venv\Scripts\python.exe ml/purchase/v2_summarize.py
```

Run GPU jobs sequentially and stop other model inference first. The evaluation driver runs the new adapter, the old regression set, the untuned base using the same line protocol, the old adapter on the new holdout, and the diagnostic robustness probes. This distinguishes a combined system change from the effect of fine-tuning with the same new protocol. Dataset and adapter hashes are recorded with results. Adapter weights remain local and ignored by Git; the repository contains reproducible recipes and predictions.

## Candidate serving

Read `selectedStep` from `output/purchase-ml-v2/training/result.json` and pass that checkpoint explicitly:

```powershell
.\ml\.venv\Scripts\python.exe ml/purchase/v2_serve.py --adapter ml/checkpoints/purchase-lora-v2/checkpoint-SELECTED_STEP
node scripts/purchase-worker.mjs --candidate
```

The adapter binds only to `127.0.0.1:4182`, rejects browser origins, serializes GPU requests, bounds body/source/context/output sizes, and has a 100-second inference deadline. It batches at most eight lines. The Node worker still applies the canonical source-evidence validator and the cloud still requires owner review before insertion. Starting this worker processes queued purchase drafts across the app's users; it is not a harmless benchmark command. The report states whether the candidate was left running. Credential renewal and an always-awake laptop are still necessary; free Render does not become a GPU host.

For the isolated local integration experiment, start only the candidate server in one terminal and run `node scripts/experiment-purchase-v2-local.mjs` in another. This uses synthetic requests and the existing Node validation path without claiming cloud jobs. The recorded run passed 5/6; the content failure is deliberately retained. Stop the server after the experiment. The candidate remains experimental: broader diagnostic probes passed only 8/15.

One garment per source line is a deliberate limit. Several garments in one line, free-form prose, unsupported quantities, multilingual purchases and novel garment categories require review. A passing synthetic benchmark cannot establish that every garment will be found.
